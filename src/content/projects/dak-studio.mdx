## 为什么做

最开始只是想从 Demo 里拿到比记分板更多的数据。真正做下去以后，问题很快从“还能算什么”变成了“这个结果到底值不值得相信”。

如果一个分析结果只能停在一个数字上，用户很难知道它来自哪些样本、发生在哪一回合，也很难判断算法到底是在描述事实，还是已经跨到了推断。DAK 后来的产品方向因此逐渐收敛到一件事：**关键分析尽量保留到比赛、回合和 tick 的证据链，让人可以自己回到 2D 回放核对。**

## 从“算一个数字”到“能自己核对”

DAK 的分析路径不是“统计 → 结论”就结束，而是尽量继续往下落到可以核验的样本：

```text
分析结果 / Finding
↓
具体样本 / Evidence
↓
比赛 / 回合 / tick
↓
2D Replay
↓
返回原来的分析问题
```

0.8 又把这条路径从零散的“统计跳回放”升级成统一的分析上下文：看完证据以后，仍然知道自己刚才在分析谁、哪些比赛、和什么基线比较，以及为什么来到这个样本。

## 不同分析，不同证据强度

DAK 没有把“已经能算出来”当成“已经可以下结论”。仓库里长期维护稳定性分级，并把样本、数据完整性、几何依赖和降级条件当成产品信息的一部分。

| 状态 | 作品集里怎么理解 | 代表能力 |
| --- | --- | --- |
| **Stable** | 口径已有固定验证依据，可作为稳定分析使用 | 基础比赛事实、ADR / KAST / K-D、经济与转化、单场 RR、2D Replay / EvidenceLink |
| **Beta** | 已经可用，但仍需要验证集或更多数据质量约束 | 对枪三分类、枪法机制、反应 / 预瞄、Flash Value、Lineup Library、跨场 RR / PRISM |
| **描述性探索** | 先忠实展示空间事实，不自动推断战术意图或“弱区” | RadarField / 控图覆盖场 |
| **Experimental** | 用来探索模式，不直接包装成确定战术判断 | Coach TacticalCluster / PatternExplorer、Anti-strat 文本 |

这个边界本身就是产品的一部分：**能算出来，不等于应该把它说成答案。**

## 从一个桌面产品到共享分析层

DAK 后来遇到的另一个问题是：同一套统计和证据能力不应该只属于 Studio。RivalHub 也需要赛事级聚合和 Demo Evidence，如果分析逻辑全部写死在桌面 UI 里，两边会不断复制口径。

现在的边界更接近：

```text
.dem
→ cs2df
→ cs2-demo-format / 3.x ZIP
→ @cs2dak/core / cohort / presentation / tournament
→ DAK Studio / RivalHub
```

其中 v3 ZIP 是 Python 解析和 TypeScript 分析之间唯一的运行时数据接缝；共享分析包负责产品中立的事实与 View Model，Studio 和 RivalHub 分别负责自己的业务上下文和界面。

## 当前边界

作品集这里固定的是 **v0.8.2 这个已发布 checkpoint**，不是把 roadmap 上所有方向都写成已经完成。后续仍会继续做 Actionable Review、Coach preparation、战术板、BP 策略和地图控制价值模型；这些在当前页面只作为后续方向，不作为现有能力证明。

DAK Studio 产品层使用 AGPL-3.0-only；共享的 `@cs2dak/*` 包与 Python 壳使用 MIT。许可证边界与代码边界保持一致：其它产品可以复用分析能力，但不需要把 Studio 整个搬过去。
