  - 默认本地导入和保存，不要求账号，也不把 demo 上传到服务器。

  - RivalHub、Studio 和后续其它工具最好复用同一套算法，不要各写一份。
  - 展示出来的统计最好能回到具体回合和 tick，而不是只剩一个总分。
approach: 我把 cs2-demo-format/3.x ZIP 定成 Python 和 TypeScript 之间的固定接口，再把分析逻辑、展示层和 Studio 桌面壳继续拆开。这样解析器升级、算法迭代和产品界面可以各自变化，不需要每次一起重写。
keyDecisions:
  - decision: v3 ZIP 是 Python 和 TypeScript 之间唯一的运行时接缝
    reasoning: 两边不直接 import 对方内部对象，格式变了就通过 schema/version 明确处理。这样不会出现“前端刚好依赖了某个 Python 内部字段，结果解析器一改全坏”的情况。
    alternatives:
      - Python 和前端直接共享内部对象
      - 每个产品自己重新解析 .dem
  - decision: 指标要能回到具体证据
    reasoning: 看一个评分没有太大意义，至少要知道它对应哪场比赛、哪一回合、哪个 tick。现在很多分析结果都可以继续跳回 2D 回放核对。
    alternatives:
      - 只展示聚合评分
      - 只让模型解释最终统计
  - decision: 分析逻辑不写死在 Studio 里
    reasoning: RivalHub 也需要这些分析。如果算法全部放在桌面 UI 里，之后每个产品都得重写一遍，所以共享的 core / presentation 和 Studio 本身分开维护。
    alternatives:
      - 所有分析都写进 Studio
      - RivalHub 单独维护一套统计

## 为什么把 Studio 和分析库分开

DAK Studio 用 AGPL-3.0-only；共享的 `@cs2dak/*` 包和 Python 壳用 MIT。许可证边界和代码边界是一致的：其它产品可以直接复用分析能力，但不需要把 Studio 整个搬过去。
