constraints:

  - HUD / Radar / Program 必须可以脱离 RivalHub 运行；RivalHub 只能作为第一方赛事上下文提供方。

approach: 先冻结 Runtime、身份、连续性、Projection 和 Local Protocol 等基础，再在其上实现 HUD、Radar 与 Operator；对高风险决策使用 ADR，对未完全冻结的产品假设使用 RFC。研发上大量使用 Coding Agent、多 Worktree 和 CI，但通过冻结规格、职责边界和真实环境验收控制并行开发带来的漂移。
keyDecisions:
  - decision: Core 只维护一份 RuntimeState，不把整个状态直接广播给所有消费者

    alternatives:
      - 把一份巨型 BroadcastState 直接通过 WebSocket 广播
      - 让每个前端消费者各自解释 Raw GSI
  - decision: Program 与 Observer Assist 做硬隔离，而不是两个可互相切换的数据源
    reasoning: No-delay 时间轴只用于机器解析 future cue；Delayed Program 才是真正的正式节目时间轴。Lookahead 断流只应关闭 Assist，不能自动变成 Program fallback，更不能把未来信息送进 OBS。
    alternatives:
      - Program 故障时把 no-delay feed 切成正式节目
      - 把未来位置和事件直接叠到正式 Radar
  - decision: 独立模式和 RivalHub 连接模式共用同一套 Runtime
    reasoning: RivalHub 能提供更完整的 Match / Roster / BP / Branding，但不能成为 HUD、Radar 或 Program 的运行前置条件。两种模式只在 MatchContext 的来源不同，不复制第二套 runtime、identity 或 radar domain。
    alternatives:
      - Broadcast 只作为 RivalHub 的附属工具
      - 为独立模式做一套简化版分叉

## 当前能展示什么

当前仓库已经可以展示真实的 Program / Operator 页面、Gameplay HUD、Radar、运行诊断、HUD 配置与测试场景。完整的制播工作区和 Lookahead 仍在开发，因此这个案例会明确区分“已经工作的能力”和“下一阶段”。

## Lookahead 为什么不是“AI 自动导播”

第一层 Observer Assist 只想解决一个很窄的问题：**在正式延迟节目到达前，让同一个解说兼 OB 提前几秒知道下一次可靠击杀事件。**

```text
+5.2s
playerA → playerB
```

系统负责给人反应时间，人继续决定切谁、讲什么。当前 RFC 明确不把 AI / LLM camera model、自动 TAKE、Future Radar 或重要性排名当成第一层目标。
